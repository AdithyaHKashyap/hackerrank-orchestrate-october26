## Goal and contract

Build a runnable, deterministic deletion auditor using only `dataset/`. For each of 518 requests, decide whether deletion was authorized; resolve current and historical identity; reconstruct state at the request's `audit_at`; apply `deletion_rules.csv`; find remaining data and active sync/restore risks; and emit evidence-backed findings, ordered remediation, and verification. Root `output.csv` must have the exact header `case_id,deletion_status,steps_json`, 518 rows sorted by case ID, valid step arrays, allowed phases/operations/states, and supported evidence citations. Later evidence and workflow/activity claims cannot prove earlier resource state. Missing or failed inspections do not prove absence; required retained records and redacted tombstones must be handled correctly.

## Architecture

1. **Phase 1 — Contract/repository analysis:** documented in [repository_analysis.md](./evaluation/repository_analysis.md).
2. **Phase 2 — Deterministic ingestion and normalized facts:** Python standard-library package at `code/deletion_audit/`; schema-checked CSV loaders; dataclasses/enums for requests, identity snapshot/events, activity, rules, evidence files/facts, inspection status, identity match and provenance; UTC timestamp parser and `audit_at` evidence filtering; exact case-folded current/historical email resolver that preserves match source/provenance and reports ambiguity without choosing a user.
3. **Phase 3 — Request authorization classification:** deterministic lexical classifier at `code/deletion_audit/request_classifier.py`; distinguishes deletion from access, correction, export, marketing opt-out, and other support intents; represents positive, negated, and mentioned-only deletion cues; mixed intent is retained; conflicting or unestablished intent is `UNCERTAIN`.
4. **Phase 4 — Time-bounded identity links:** `code/deletion_audit/identity_links.py` combines current snapshots, historical email/phone/hash transitions, and evidence aliases explicitly paired with a known stable user ID. Links retain validity intervals, match source, confidence, and provenance. Resolution separates identifier validity time from the `audit_at` knowledge cutoff; conflicting subjects are ambiguous, while unresolved-time or OCR-derived links remain candidates.
5. **Phase 5 — Evidence ingestion and indexing:** `code/deletion_audit/evidence_index.py` builds a reusable deterministic index from JSON, SQLite-compatible SQL, logs, the structured text handover, and local PDF/image extraction. Text PDFs use PyPDF2; scanned PDF pages can be rendered with pypdfium2 and OCRed locally with pytesseract/Tesseract. OCR facts retain page/region locators, bounding boxes, engine/version, and confidence metadata and remain inconclusive. Timestamped JSON records are confirmed PRESENT only when their source shape explicitly scopes a direct resource row (`snapshots[].records[]` or mapped `service_exports` records). Nested document/profile values retain their parent resource and observation time; this does not establish inventory completeness or absence.
6. **Phase 6 foundation — Evidence reconciliation and coverage ledger:** `code/deletion_audit/evidence_reconciliation.py` partitions request-related indexed records as eligible, excluded, or temporally unresolved; groups only records with explicit system/resource/category keys; classifies direct state, workflow claims, data-flow observations, or unclassified evidence; and preserves all provenance. It associates explicit `subject_reference` values only when they exactly match a strong subject email alias or stable user ID. Per-resource coverage remains conservative; absence requires an explicit direct ABSENT inspection, a caller-declared complete-source scope, and a successful source report available by the cutoff.
7. **Phase 7 — Grounded coverage:** `code/deletion_audit/coverage_grounding.py` normalizes explicit SQL table/collection relationships, JSON snapshot parent context, and a closed mapping for observed `service_exports` paths whose resource categories exist in deletion rules. Nested search documents inherit their explicit query observation time; HTTP 404 lookup rows are not treated as present or absent. Complete inventory scopes are derived only from successfully extracted SQL with matching `snapshot_completed_at` and `snapshot_scope` declarations. JSON/service-export rows may establish positive presence but never complete-source absence. `EvidenceGrounder` reuses one normalized `EvidenceIndex` and source-contract inventory across requests. Activity identity links must name a resource, user ID, and email that independently resolves to the same unambiguous subject; operational activity is joined only by exact resource/system links. Activity records remain claims, and later rows are excluded at each request cutoff.
8. **Phase 8 — Policy-aware assessment:** `code/deletion_audit/policy_assessment.py` evaluates the supplied rule conditions and DELETE/REDACT/ANONYMIZE/RETAIN actions per grounded scope, returns `SATISFIED`, `VIOLATED`, or `UNKNOWN`, and retains evidence IDs and provenance. Missing/unsupported categories are explicit UNKNOWN assessments; potential exposed identifiers are surfaced separately. Conflicts, unresolved time, incomplete inspection, and operational activity claims are not upgraded into state confirmations.
9. **Phase 9 — Evidence gap closure and recreation graph:** `code/deletion_audit/recreation_graph.py` models subject-linked resources and evidence-backed copy, sync, backup, restore, and activity relationships. Explicitly configured flows/restores are distinguished from operational claims; uncertain edges and provenance remain visible and every edge is cutoff-aware. Grounding now maps additional observed SQL tables/fields, but unsupported scope mappings remain unknown.
10. **Phase 10 — Decisions and remediation:** `code/deletion_audit/decision_engine.py` maps evidence-supported cases only to `COMPLETE`, `INCOMPLETE`, or explicitly unauthorized `NOT_APPLICABLE`; it creates findings, dependency-aware remediation, and verification steps. It fails closed when the evidence does not support an allowed status or complete verification.
11. **Evaluation/output runner:** `code/main.py` builds one shared evidence index per invocation and evaluates either all requests or `sample_deletion_requests.csv`. `--sample-only` writes decided rows to separate `code/evaluation/sample_predictions.csv` and scores them after generation; the reference never feeds predictions. Full output is written atomically only when every case is decidable and the validator passes. Current full run remains blocked, so no root `output.csv` is emitted.
12. **Evaluation reports and packaging:** pending. The required full-dataset evaluation/usage reports and submission archive have not been generated.

The implementation must keep extraction/provenance separate from policy/output logic. Any candidate facts must retain file/activity/audit identifiers and timestamps; later filtering is by each request's cutoff. A model may assist only with cited extraction, never invent evidence or override deterministic policy.

## Important decisions and risks

- Request identity matching uses exact normalized email only; typed current/history links also model phone and email hashes. A conflicting set of users returns `AMBIGUOUS`, and no fuzzy fallback is allowed. Evidence aliases require an explicit known stable user reference.
- Current identity snapshots are cutoff-filtered by `updated_at`; historical email transitions by `event_time`. Each match carries its source ID and availability time.
- A prior email remains usable as a historical identity link after its end time if that history is known by `audit_at` and no active link claims the email at `requested_at`. If an active owner exists, request-time ownership takes precedence; multiple expired prior owners are ambiguous. Treat this as a challenge-data-backed interpretation, not a universal account-ownership rule.
- Evidence eligibility requires a non-null `available_at` at or before `audit_at`; a fact with a later `observed_at` is excluded. The index keeps a separate unresolved bucket for missing content-level timestamps. A confirmed inspection must state `PRESENT` or `ABSENT`; extracted facts stay inconclusive and cannot confirm either. This is a foundation, not proof that every source has been inspected.
- Phase 6 only establishes absence when the caller explicitly declares a complete evidence ID for the exact resource/category scope and that source's extraction report is `SUCCESS` and captured by `audit_at`. The caller must ground this completeness declaration in source semantics; `SUCCESS` parsing alone is not completeness. Unknown/incomplete scopes remain inconclusive or not inspected. No Phase 2 models or temporal APIs were modified.
- **Temporal coverage compatibility issue (not changed):** `filter_evidence_for_request` in Phase 2 returns only facts whose `available_at` is non-null and at/before the cutoff. A timestamp-less fact is therefore excluded from the returned list, with no separate “temporally unresolved” collection or coverage count. Preserve the original facts or add an explicit eligible/unresolved partition before callers use the filtered list as coverage. Phase 2 was left unchanged; obtain approval before changing its API.
- CSV schemas are based on actual participant files. Header, row width, required fields, timestamp parsing, allowed reported status, and duplicate record IDs are validated. `sample_output.csv` and `output.csv` are schema-checked but not loaded as decision inputs.
- High accuracy risks remain: multilingual intent classification, decoy/global activity, 1,331 scopes without supported policy categories, missing direct state/inspection evidence, replica drift, temporal leakage, conditional retention/redaction/anonymization, sync/restore recreation, and evidence extraction uncertainty.
- Challenge docs conflict on evaluation report location (`evaluation/` vs `code/evaluation/`); README and current repository layout use `code/evaluation/`. Resolve before packaging.
- The October deadline is not configured. Do not infer one.
